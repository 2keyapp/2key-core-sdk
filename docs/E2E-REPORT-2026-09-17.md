## 1. Executive summary

Queued machine enrollment works end-to-end on billing v1:

1. Owner session → org kickstart (Entity CA keys stay on the **owner** laptop).
2. Machine generates a CSR; the private key never leaves the **device**.
3. Owner approves from the CSR inbox (owner-only).
4. Billing validates the CSR and the Entity-CA leaf, then the **Host key** issues a Platform-endorsed certificate.
5. `machine pull` stores `platform-endorsed.crt`.
6. HAProxy with `ca-file` = Platform Root PEM and `verify required` accepts that client cert over TLS 1.3 and returns HTTP 200. Presenting `machine.crt` instead is rejected (`tlsv1 alert unknown ca`).

Also proven in this session:

- Formal **split enroll**: admin dir has Entity CA private key and no `machine.key`; device dir has `machine.key` and no Entity CA key.
- Live **`idr machine renew --yes`** on the rebuilt CLI (D1 fix): SKI rotated, new endorsed leaf verifies, old SKI marked `renewed`.
- **PEP-style AuthZ** (no product PEP process in-repo): credential JWS verifies with the Entity CA, `credential-status` is `active`, `authorize(machine.connect)` allows the machine host and denies other hosts / `admin.invite`, `assert-subset` accepts attenuation from a delegable parent and rejects over-permission.

Three CLI mismatches from the first run (mTLS attach on renew/decommission, stale `csr show` status, `decommissioned` filter) were **fixed the same day**, covered by unit tests, and `idr` was rebuilt. Live renew after that rebuild succeeded.

| Owner      | Fresh throwaway accounts; role **owner** after bind                                  |

Machine AuthN HTTP is **billing**, not Better Auth `/delegate-permissions/*`. Better Auth is used for the human session and PKI helpers (CSR bind, Host CA, endorsement, `authorize`). CSR approve remains **organization owner only**.

A Host CA PEM path was added on billing for this work: `GET /platform-root` returns `platformRootPem`, and enroll-approve issues an X.509 Platform-endorsed leaf (previously only a JWS envelope over cert DER). Without that, HAProxy `ca-file` cannot work.

## 4. Architecture under test (short)

```
Device                         Billing                         HAProxy (local :9443)
─────                         ───────                         ─────────────────────
machine.key (never sent)
machine.csr  ──────────────►  validate CSR
                              owner signs leaf with Entity CA
                              Host key endorses same SPKI ──►  ca-file = Platform Root PEM
machine pull ◄──────────────  platform-endorsed.crt           verify required
                                                              HTTP 200 "mtls-ok"
```

| Material                        | Where it lives                                       | Role                                            |
| ------------------------------- | ---------------------------------------------------- | ----------------------------------------------- |
| Host (Platform) **private** key | Billing (`PLATFORM_COSIGN_JWK`, or ephemeral in dev) | Signs Platform-endorsed leaves                  |
| Platform Root **PEM**           | `GET /platform-root` → HAProxy `ca-file`             | Trust anchor                                    |
| Machine **private** key         | Device `identity/machine.key` only                   | Client key presented _to_ HAProxy               |
| `platform-endorsed.crt`         | Device, after pull                                   | Client cert HAProxy must accept                 |
| `machine.crt`                   | Device                                               | Entity-CA leaf; **not** the HAProxy client cert |

The Host private key must **not** be installed on HAProxy. HAProxy only needs the public Platform Root.

### 5.4 Live HAProxy mTLS — **PASS**

Ephemeral HAProxy 3.2 on `127.0.0.1:9443`:

```
bind 127.0.0.1:9443 ssl crt <server.pem> \
  ca-file <platform-root.pem> verify required
```

`ca-file` was the Platform Root from the **device** after split pull (same bytes as `GET /platform-root`). Server cert was a throwaway RSA leaf for localhost (HAProxy bind), unrelated to the Host CA.

| Client material                                | Handshake                                          | HTTP              |
| ---------------------------------------------- | -------------------------------------------------- | ----------------- |
| `platform-endorsed.crt` + `machine.key`        | TLS 1.3 **CONNECTION ESTABLISHED**, peer verify OK | **200** `mtls-ok` |
| `machine.crt` + `machine.key` (Entity-CA leaf) | **tlsv1 alert unknown ca** (alert 48), exit 1      | —                 |

That is the product rule: the terminator must see the Host-endorsed leaf, not `machine.crt`.

### 5.6 M2M AuthZ (PEP checks) — **PASS** (no PEP daemon)

There is no product PEP in this repo. A PEP is specified as: (1) mTLS AuthN, (2) credential first frame, (3) signature + subset/`authorize` + not revoked. We exercised those checks against the live split-enroll credential:

| Check                                                                                       | Result                                                                                |
| ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| AuthN                                                                                       | HAProxy mTLS (§5.4)                                                                   |
| Credential JWS                                                                              | `compactVerify` with Entity CA public JWK → **ok**; `issuerSki` matches Entity CA SKI |
| `GET credential-status?ski=`                                                                | **active**, host `laptop--e2e-f322f491.test`                                          |
| `authorize(grants, machine.connect, {name: laptop, entity})`                                | `{ ok: true }`                                                                        |
| Same action, host `other`                                                                   | `{ ok: false, NOT_AUTHORIZED }`                                                       |
| `admin.invite`                                                                              | `{ ok: false, NOT_AUTHORIZED }`                                                       |
| `POST assert-subset` parent = delegable `machine.connect` `name:""`, child = machine grants | `{ ok: true }`                                                                        |
| Child `admin.invite` vs that parent                                                         | `{ ok: false, SUBSET_VIOLATION }`                                                     |
| `cargo test -p dp-rust conformance_fixtures`                                                | **ok**                                                                                |

A machine credential with `delegable: false` cannot be used as an `assert-subset` **parent** (identical child/parent was `SUBSET_VIOLATION`). That is correct algebra: PEP **authorize** is the “may this machine connect” check; **assert-subset** is for issuing attenuated children from a **delegable** parent.

Not proven: a process that reads a `dp.credential.v1` first frame off the socket. The stored credential and algebra are the same objects that frame would carry.

## 8. Recommendation

**The queued-enroll + Host PEM cosign path is proven on local billing**, including a real HAProxy handshake and live key renewal after the CLI fixes.

Remaining product gaps worth tracking, not blockers for this local verdict:

1. Non-owner negative case on CSR approve (`OWNER_REQUIRED`).
2. Device-only renew (today the Entity CA must be on the renewing laptop).
3. A PEP that consumes `dp.credential.v1` as the first app frame.

`enroll-instant` remains explicitly out of billing v1.
